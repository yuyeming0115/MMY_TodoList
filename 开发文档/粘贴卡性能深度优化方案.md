# 粘贴卡性能深度优化方案

> 创建日期：2026-05-22
> 状态：**部分实施**（B + C 已完成）
> 前置文档：`剪贴板优化实施方案.md`、`clipboard-performance-optimization.md`

## 1. 现状与问题

已实施的优化（v1.5）：虚拟滚动、图片缩略图、过期清理。

**仍然卡顿的根本原因：**

| 问题 | 位置 | 影响 |
|------|------|------|
| 拖拽模式强制全量渲染 | ClipboardPanel.vue:416 | 拖拽时 DOM 节点数 = 数据总量 |
| 精简模式无实质优化 | ClipboardPanel.vue:575 | 只改 padding，渲染逻辑完全相同 |
| 虚拟滚动阈值过高（100项） | ClipboardPanel.vue:34 | 50-99 项时全量渲染 |
| 每卡片 9 个事件监听器 | ClipboardItemCard.vue | 100 项 = 900+ 监听器 |
| 批量操作逐个触发 store 更新 | clipboardStore.ts | 每次操作触发一次完整重渲染 |
| 图片 Base64 无内存缓存 | lib.rs | 相同图片重复解码 |

## 2. 竞品参考

### Ditto（Windows，开源）
- 使用 **SQLite FTS5** 全文索引，搜索 10 万条记录 < 0.03s（普通查询需 22.5s）
- 图片存文件系统，DB 只存路径，启动时不加载图片数据
- 列表使用 Windows 原生虚拟列表控件，DOM 节点恒定

### Maccy（macOS，开源）
- 菜单弹出时才加载数据，**按需渲染**，不预加载全部历史
- 搜索走本地 SQLite，不在内存中过滤
- 图片只生成一次缩略图并持久化，不重复计算

### CopyQ（跨平台，开源）
- 使用 Qt 的 `QAbstractItemModel` + 虚拟视图，**永远只渲染可见行**
- 图片解码在独立线程，不阻塞 UI 线程
- 批量操作使用事务，一次提交，一次重渲染

### 核心共识
> 所有高性能剪贴板管理器的共同点：**UI 线程只做渲染，数据处理全部异步/后台**。

## 3. 更高效的优化方案

### 方案 A：事件委托替代逐卡监听器（改动小，收益高）

**原理：** 把 9 个 × N 个监听器，合并为列表容器上的 1 个监听器，通过事件冒泡 + `data-id` 属性识别来源。

```
当前：每张卡片 × 9 个监听器 = 900 个（100 张卡）
优化后：列表容器 × 1 个监听器 = 1 个（无论多少张卡）
```

**实施位置：** `ClipboardPanel.vue` 列表容器层，`ClipboardItemCard.vue` 改为只发射原生 DOM 事件。

---

### 方案 B：降低虚拟滚动阈值 + 精简模式专用渲染

**原理：**
- 虚拟滚动阈值从 100 降到 **20**，20 项以上即启用
- 精简模式使用简化卡片组件（去掉操作按钮区域、减少 DOM 层级），每张卡片 DOM 节点数从 ~15 个降到 ~5 个

**效果：** 精简模式 100 张卡的 DOM 节点数从 1500 降到 500。

---

### 方案 C：批量操作事务化（改动小）

**原理：** 批量删除/移动分类时，前端收集所有 ID，一次性调用后端批量接口，后端用 SQLite 事务一次提交，前端 store 只更新一次。

```
当前：删除 50 张 = 50 次 store 更新 = 50 次重渲染
优化后：删除 50 张 = 1 次 store 更新 = 1 次重渲染
```

**实施位置：** `clipboardStore.ts` 批量操作方法 + Rust 新增 `batch_delete`、`batch_update_category` 命令。

---

### 方案 D：图片解码移入 Web Worker（改动中等）

**原理：** Base64 → Blob URL 的解码操作放到 Web Worker，主线程只接收解码完成的 `ImageBitmap`，不阻塞滚动和交互。

```
当前流程：主线程解码 Base64 → 渲染（阻塞 UI）
优化流程：Worker 解码 → postMessage(ImageBitmap) → 主线程直接渲染（不阻塞）
```

**实施位置：** 新建 `imageDecoder.worker.ts`，`ClipboardItemCard.vue` 图片加载改为走 Worker。

---

### 方案 E：SQLite FTS5 全文搜索（改动中等，参考 Ditto）

**原理：** 当前搜索是前端 JS 过滤内存数组，数据量大时每次输入都全量遍历。改为 SQLite FTS5 虚拟表，搜索直接走数据库索引。

```sql
CREATE VIRTUAL TABLE clipboard_fts USING fts5(content, item_id UNINDEXED);
```

**效果：** 10 万条记录搜索从 ~500ms 降到 < 5ms（SQLite 官方数据：FTS5 比普通查询快 750 倍）。

**实施位置：** Rust `database.rs` 新增 FTS 表，`search_clipboard_items` 命令改走 FTS 查询，前端搜索改为防抖后调用后端接口。

---

### 方案 F：启动时分页加载（改动小）

**原理：** 参考 Maccy，启动时只加载最近 50 条，滚动到底部时加载更多（无限滚动），而不是全量加载到内存。

**效果：** 启动速度与数据总量解耦，1000 条和 10 条启动速度相同。

**实施位置：** Rust `get_clipboard_items` 增加 `limit/offset` 参数，前端 store 改为追加模式。

## 5. 已实施优化详情

### 方案 B：降低虚拟滚动阈值 + 精简模式专用渲染（2026-05-22）

**修改内容：**
1. 虚拟滚动阈值从 `100` 降到 `20`（`ClipboardPanel.vue:34`）
2. 精简模式下不渲染拖拽手柄、锁定角标、过期提示（`ClipboardItemCard.vue`）

**效果：**
- 20 项以上即启用虚拟滚动，减少 DOM 节点数
- 精简模式每卡片 DOM 节点数从 ~15 个降到 ~8 个

### 方案 C：批量操作事务化（2026-05-22）

**修改内容：**
1. Rust 后端新增 `batch_delete_clipboard_items`、`batch_update_clipboard_items_category` 命令（使用 SQLite 事务）
2. 前端 `removeItems`、`batchUpdateItemsCategory` 改为调用批量命令

**效果：**
- 批量删除 50 张 = 1 次 store 更新 = 1 次重渲染
- 批量移动分类 50 张 = 1 次 store 更新 = 1 次重渲染

### 方案 F：启动分页加载（2026-05-22）

**修改内容：**
1. Rust 后端新增 `get_clipboard_items_paginated(limit, offset)`、`get_clipboard_items_count` 命令
2. 前端启动时只加载最近 50 条，滚动到底部时加载更多
3. store 新增 `hasMore`、`loadMore` 方法

**效果：**
- 启动速度与数据总量解耦，1000 条和 10 条启动速度相同
- 消除第一次操作的"冷启动"卡顿
